# Student 1 frontend service

This FastAPI + Jinja + HTMX frontend renders TripGenie's Trip & Itinerary Management UI and talks to the Student 1 backend over HTTP only.

## Environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `STUDENT1_FRONTEND_BACKEND_BASE_URL` | `http://student-1-backend:8001` | Base URL for the Student 1 backend service. |
| `STUDENT1_FRONTEND_BACKEND_API_PREFIX` | `/api` | Backend public API prefix used for CRUD requests. |
| `STUDENT1_FRONTEND_BACKEND_TIMEOUT_SECONDS` | `5` | Timeout for frontend-to-backend HTTP calls. |
| `STUDENT1_FRONTEND_RAG_TIMEOUT_SECONDS` | `150` | Timeout for the knowledge-base (RAG) question only; must exceed the backend's 130 s RAG timeout. |
| `STUDENT1_FRONTEND_MCP_TIMEOUT_SECONDS` | `210` | Timeout for the trip assistant (MCP via AI-Mode) only; must exceed the backend's `STUDENT1_BACKEND_MCP_TIMEOUT_SECONDS` (200 s). |
| `STUDENT1_FRONTEND_MULTI_AGENT_TIMEOUT_SECONDS` | `60` | Timeout for each multi-agent planner call (start, status poll, decision). Runs are asynchronous on the server, so none waits for the agents; a decision also saves the approved items. |
| `STUDENT1_FRONTEND_SERVICE_NAME` | `student-1-frontend` | Service name reported by frontend health endpoints. |
| `STUDENT1_FRONTEND_ACCOMMODATION_UI_URL` | `http://localhost:9003` | Where a **browser** reaches student 2's webpage. A row in the Accommodation section links there, so this is the address on the user's machine, not the compose hostname this container would use. |

## Runtime notes

- The page loads the team-owned `theme.css` contract from the shared portal (`TRIPGENIE_PORTAL_URL`, default `http://localhost:8080`) before Student 1's feature stylesheet, matching the shared portal and the other themed student frontends. Student 1 keeps only layout and feature-state styling locally.
- HTMX 2.0.4 is packaged with the frontend and served from its own `/static` mount, so CRUD navigation does not depend on a public CDN and generated asset URLs retain any application root path.
- The UI keeps **UI mode** and **AI mode** visually distinct. Issue #12 replaces the disabled placeholder with an accessible AI suggestion form and HTMX result states.
- Form submissions preserve entered values and show backend field/general errors for both normal page loads and HTMX swaps.
- AI results are always labelled as drafts and route users into the normal itinerary-item create form for review/edit/save. There is no silent bulk persistence path.
- AI-mode preserves entered values on backend/model validation failures and keeps CRUD usable when the shared AI-Mode dependency is unavailable.
- Each home and trip page reads the backend's `GET /api/ai-features` and leaves out any AI panel (AI suggestions, knowledge base, trip assistant, Plan my itinerary, the home-page AI teaser) that the backend configuration switches off, e.g. the cloud profile. If that read fails the panels stay and the backend's own errors answer; an AI service that is merely down does not hide anything.
- The trip page has an **Accommodation** section listing what is booked for that trip: name, the check-in and check-out (with times when recorded), and what the stay costs. The name and price come from student 2 by way of this service's backend, and are shown as the accommodation id and a dash when that service cannot be reached.
- Clicking a row opens that accommodation on student 2's own page (`/?accommodation=<id>`), because that is the service that owns it. The bin on each row goes to the same confirmation screen pattern as deleting an itinerary item — it removes the accommodation from the trip, not the accommodation itself.
- Release 1 adds two trip-page panels. **Ask the knowledge base** (`POST /trips/{id}/rag-query`) shows the grounded answer, a confidence badge and its citations, or a distinct "not enough information" state with no answer text. **Ask the trip assistant** (`POST /trips/{id}/mcp-options`) sends an optional request ("Find a mid-range stay and a food activity") and country to the backend, where the AI model behind shared AI-Mode chooses and calls the MCP tools itself. The panel shows the model's summary, its options (marked "not verified against tool results" when no tool returned them), and a card per tool the AI called with its arguments, status, duration and a readable result summary, plus warnings for hidden ungrounded options or any write tool. Nothing is saved; options are added through the existing sections. An optional country fills in city-only destinations. HTMX swaps only the panel; without JavaScript the whole trip page is returned. Disabled, unavailable, timeout, "AI used no tools", validation and malformed responses each render their own state.
- Release 2 adds **Plan my itinerary** (`POST /trips/{id}/multi-agent-plan`), backed by the backend's multi-agent routes. Starting a plan returns at once; while the Planner, Worker and Reviewer work, the panel polls `GET /trips/{id}/multi-agent-plan/{runId}` every 3 s with ordinary HTMX (`hx-trigger="every 3s"`), shows which stage is running in a `role="status"` region, and stops polling when the run is ready, decided or failed. Polls do not move keyboard focus (`data-preserve-focus` in `app.js`). Without JavaScript a **Refresh status** link loads the same URL as a full trip page. A ready plan shows the Planner's plan, each agent step with its MCP tool calls (after a revision, both attempts, including a failed Worker step and its error), the deterministic checks, the Reviewer's verdict, issues and risks, and every drafted item with its evidence id, blocking problems and warnings (clashes, unsupported sources). The traveller then chooses **Approve all items**, **Save selected items** (partial), **Save corrections** (the ticked items with their edits) or **Reject plan** (`POST …/{runId}/review`). Items that cannot be saved as drafted start unticked. A refused decision re-shows the plan with the traveller's edits and names the item at fault. The result says exactly what was saved, already saved or failed — "Only 1 of 2 approved items" rather than success — and a failed save offers **Retry saving the missing items**, which repeats the recorded decision so nothing is written twice. Disabled (`MULTI_AGENT_DISABLED`), unavailable, timeout, busy, already-decided and malformed responses each render their own state; all text from the agents is HTML-escaped.
- `GET /health` reports frontend health plus backend dependency status. `GET /ready` returns `503` until the backend dependency is ready. These operational endpoints are TripGenie service decisions for Release 0.
